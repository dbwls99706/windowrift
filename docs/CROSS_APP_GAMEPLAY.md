# Cross-application gameplay: Minecraft and DOOM

## Demonstration matrix

| Source | What is outside its window? | Control | Native game state preserved? | Can return original? |
| --- | --- | --- | --- | --- |
| Minecraft Classic | Pixel-derived blocks on the **real X11 desktop** | Mouse: place/mine/paint | No, visually separate desktop world | No native transfer |
| Minecraft Java 1.21.1 | Native UUID-backed living mob **projection** | Keyboard: move/jump/drop/sprint; mouse: drag | Yes, same tagged mob stays in a force-loaded server-side vault | Yes, verifies UUID and restores flags |
| DOOM shareware 1.9 | Frames decoded from a **user-supplied WAD** | Keyboard: move/jump/drop/sprint | No, the game process is unchanged | Not applicable |
| Undertale, GTA and arbitrary EXE | No verified live state adapter | Visual cutout controls only, where available | No | No |

The gameplay GIFs in the README are genuine screen recordings of live X11
sessions. The Minecraft native mob test uses an original Mojang *server*, not
a visible Minecraft gameplay client. The DOOM proof runs the original game and
Chrome concurrently, but only its external projection moves.

## Shared desktop block physics

The Minecraft Classic builder saves blocks to
`~/.local/share/windowrift/desktop-world.json`. Its blocks are drawn in a
real input-transparent OS-level window, not the website DOM. This world is
loaded by the Minecraft Java and DOOM desktop player processes, and polled
for changes while the players run.

The shared `desktop_step()` adapts those screen-space blocks to the same
player controller. Block top surfaces support landings and jumps; their sides
and undersides are solid. The existing desktop platforms engine also supports
jump buffering, sprint, and deliberate drop-through. Coordinates are from
the virtual desktop and may be negative on multi-monitor systems.

For the full visual effect, keep the official Minecraft Classic builder's
block overlay running while moving a Minecraft mob or DOOM Imp. If the
builder has been closed, the physics still reads its saved JSON but the block
art is no longer displayed.

### Minecraft Java controls

Use your own backed-up, trusted local dedicated server and a legitimate
1.21.1 client installation. RCON must only be accessible locally; do not use
this integration with third-party multiplayer servers.

1. Summon or explicitly tag one supported mob. See [native mob setup](MINECRAFT_MOBS.md).
2. Start `windowrift-mob --game-jar /path/to/1.21.1.jar`.
3. Click **Lift real mob**. The real server entity is moved to stasis; its
   UUID, health and restorable flags stay attached to the ledger.
4. Click **Play selected mob on desktop**, focus the control panel and use
   A/D or Left/Right, W/Space/Up, Shift and S+Space.
5. Click **Return SAME mob** to restore that UUID in the real Minecraft
   world, after ensuring the destination is safe.

A real GUI recording and same-UUID check are generated by
`scripts/ci/real_mob_gui_proof.py` in the
[real-mob workflow](../.github/workflows/real-mob.yml). It sends Qt keyboard
events through the same input path as an interactive user and checks that the
avatar moved while the original server UUID remained unchanged. It then
puts the mob back and checks UUID again.

### DOOM controls

Use a lawful shareware IWAD. Never include the IWAD or extracted sprites in
the repository. A living Chocolate Doom game window **must be visible**; the
demo refuses to run against an absent original game.

```bash
chocolate-doom -iwad /path/to/doom1.wad -window -warp 1 1 -nosound -nomusic
windowrift-doom --doom-wad /path/to/doom1.wad
```

Focus the WindowRift control panel for input. A/D or Left/Right move; W,
Space, or Up jump; Shift sprints; S+Space drops through a ledge; Esc pauses.
The actor is an input-transparent topmost native window and can travel over
unrelated application windows.

The CI proof uses `windowrift-doom --record-gif artifacts/doom-keyboard-x11.gif`
to replay Qt keyboard presses and record *actual X11 frames* for reproducible
proof; no precomputed trajectory is used. The DOOM binary is not modified.

## Reverse-engineering and executable modification

Disassembly alone does not provide a general-purpose game object interface.
The same machine instructions might be an optimizer output, a scripting
engine, or an anti-cheat-protected runtime. A robust native adapter needs
reliable entity discovery, object ownership, serialization, a reversible
transaction, cleanup on crash, and a way to reconcile positions and game
simulation steps across the desktop boundary.

An opt-in native adapter can be developed on software for which the operator
has authorization. Prefer, in this order:

1. A documented native mod/plugin/game-server API, with a reversible object
   handoff and stable engine identity.
2. A reproducible source-level instrumented build for open-source games
   (for example, an independent Chocolate Doom-based state adapter), with
   upstream version pinning and genuine roundtrip tests.
3. Disassembly or decompilation as **read-only investigative evidence**
   before implementing a per-version adapter. PE/ELF/JAR discovery currently
   stops at engine hints; it does not rewrite instructions or modify processes.

Avoid distributing patches for third-party protected games, interfering with
anti-cheat, or changing multiplayer server state without authorization.
A generic binary rewrite would not safely preserve renderer, networking,
collision or AI state and is not represented as working.

## Verification rules

- **Game-native:** original entity ID and world state verified inside the
  original game/server before and after the handoff.
- **Desktop-interactive:** user keys/mouse produce state changes on actual
  desktop windows; screenshots/GIFs come from the current display.
- **Unrelated applications:** a second real window remains operational;
  any webpage impact is reported separately from OS overlay.
- **Return and recovery:** verify the original object and fail closed if
  state or identity cannot be reconciled.
